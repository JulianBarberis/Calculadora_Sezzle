## 1. Context & Business Rationale
As a mission-critical FinTech calculation platform, the Sezzle Calculator requires a dependable, reproducible, and verifiable engineering foundation prior to introducing mathematical domain logic. Phase 0 establishes this foundation by standardizing project layout, package management, build tooling, linting, testing harnesses, and automated continuous integration (CI/CD).

---

## 2. In-Scope vs. Out-of-Scope

### 2.1 In-Scope (Phase 0 Deliverables)
- **Root Repository Configuration**:
  - Comprehensive `.gitignore` protecting against compiler artifacts, OS files, and rogue package lockfiles.
- **Backend Scaffolding (`backend/`)**:
  - Go 1.22+ module initialized as `github.com/julianbarberis/sezzle-calculator`.
  - Clean layered directory structure (`cmd/api/`, `internal/api/`, `internal/calculator/`, `internal/history/`).
  - Minimal compiling entry point in `cmd/api/main.go` verifying standard library HTTP capabilities.
- **Frontend Scaffolding (`frontend/`)**:
  - React 19 + TypeScript Single Page Application initialized with Vite.
  - Strict enforcement of `pnpm` (`pnpm-lock.yaml` only).
  - Integration of Tailwind CSS v4 via `@tailwindcss/vite`.
  - Declaration of GTA VI Neon Sunset color variables and Apple Liquid Glass utility classes.
  - Installation of `lucide-react`.
  - Vitest + React Testing Library harness configured with a passing smoke test.
  - TypeScript strict mode configuration with `type-check` script (`tsc --noEmit`).
- **Continuous Integration (`.github/workflows/ci.yml`)**:
  - Automated GitHub Actions pipeline running Backend verification, Frontend verification, and Docker configuration validation.

### 2.2 Out-of-Scope (Deferred to Future Phases)
- Mathematical domain calculation logic (`shopspring/decimal`, Newton-Raphson sqrt, integer exponentiation) $\implies$ **Phase 1**.
- REST API route handlers (`/api/v1/calculate`, `/api/v1/history`), in-memory ring buffer, and concurrency safety tests $\implies$ **Phase 2**.
- Full interactive UI components (`<Calculator />`, `<Keypad />`, `<Display />`, `<HistoryTape />`) and `useReducer` state machine $\implies$ **Phase 3**.
- Multi-stage Docker production images and end-to-end integration runner (`tests/e2e/runner.mjs`) $\implies$ **Phase 4**.

## 3. Architectural & Technical Decisions

### 3.1 Strict Package Manager Mandate (`pnpm`)
- `pnpm` is strictly enforced for all frontend operations.
- `npm` and `yarn` are strictly banned.
- `package-lock.json` and `yarn.lock` must never be generated or committed to version control.
- Rationale: Content-addressable storage, symlink-based strict dependency resolution preventing phantom dependencies, and deterministic reproducibility.

### 3.2 Lean Backend Baseline Scope
- Backend module is initialized strictly with Go standard library dependencies.
- Third-party mathematical libraries (`github.com/shopspring/decimal`) are deferred to Phase 1, keeping Phase 0 focused entirely on tooling, compilation sanity, and CI pipeline readiness.

### 3.3 Zero-`useEffect` Architectural Guardrail Establishment
- The frontend architecture establishes the non-negotiable rule prohibiting `useEffect`.
- Initial boilerplate generated by Vite will be audited and cleaned to ensure no `useEffect` hooks exist in the codebase.

### 3.4 Visual Design Tokens
- Baseline styles in `frontend/src/index.css` must embed the GTA VI Neon Sunset palette:
  - `--violet-twilight: #5644c0`
  - `--rose-kiss: #fe5ea3`
  - `--raspberry-plum: #ad3083`
  - `--petal-pink: #bb80a9`
  - `--cinnamon-wood: #bb7462`
  - `--powder-blue: #98b5cc`
  - `--lobster-pink: #b86b60`
  - `--midnight-violet: #36294b`
- Glassmorphic backdrop blur tokens (`backdrop-blur(16-24px)`), translucent white borders (`rgba(255, 255, 255, 0.15)`), and high contrast standards ($\ge 7:1$).

## 4. Operational Invariants & Guardrails
- **Go Version**: Go 1.22 or higher (local environment: Go 1.27.1).
- **Node & pnpm Versions**: Node 24+, pnpm 11+.
- **Zero Errors Policy**:
  - `go vet ./...` must report zero warnings.
  - `pnpm type-check` must report zero compilation errors (`strict: true`).
  - `pnpm lint` must pass with zero ESLint errors.
  - `pnpm test` must run with zero failures and zero `act(...)` warnings in `stderr`.
